# ТЗ и план переработки 0.2.0

Статус: реализовано в 0.2.0. Документ сохранён как история решения и критериев
приёмки. Актуальное поведение описано в [текущей документации](../current/).

## 1. Суть переработки

`network-terminal-mcp` должен делать четыре вещи хорошо:

1. открывать терминал привычной командой;
2. удерживать этот терминал открытым;
3. передавать в него ввод и возвращать новый вывод;
4. сообщать настоящую причину ошибки.

Главный принцип: **сначала рабочий и простой инструмент, затем ограничители —
только если реальная эксплуатация покажет, что они нужны**.

Версия 0.2.0 — breaking release. Структурированное описание подключения и
обязательные клиентские разрешения удаляются, а не сохраняются как второй API.

## 2. Почему переработка необходима

По сессиям OpenCode и audit 0.1.x подтверждены следующие проблемы:

- модель получает `Error executing tool open_session` вместо реальной причины;
- в audit при этом есть полезные сообщения: unknown host key, authentication
  failed, Invalid key, timeout и другие;
- структурированный `open_session` заставляет модель вручную собирать сложный
  JSON и дублировать сведения, которые уже есть в SSH config и SSH agent;
- `open_session` может отсутствовать в сокращённом Code Mode catalog;
- обязательный permission popup и credential references усложняют первый шаг;
- для одноразовых команд обычный `ssh host 'command'` остаётся проще, поэтому
  MCP не должен пытаться заменить его командным gateway.

Вывод: ниша MCP — **постоянный интерактивный терминал**, а не одноразовый
`run_command` и не повторение SSH-конфигурации в JSON.

## 3. Цели

### 3.1. Основные

- Один способ открытия сессии: `open_session(command)`.
- SSH запускается через настоящий OpenSSH в PTY.
- Поддерживаются пользовательские `~/.ssh/config`, SSH agent, aliases,
  ProxyJump/ProxyCommand, ключи, алгоритмы и другие опции OpenSSH.
- Telnet запускается как интерактивный системный клиент в PTY.
- Serial доступен короткой командой без десяти параметров.
- Нет обязательных inventory, policy, credential или connection-файлов.
- Нет обязательного `pass` и обязательного permission popup.
- Модель получает конкретные ошибки запуска, подключения и терминального I/O.
- Сохраняются persistent sessions, bounded output buffer и cursor-семантика
  чтения без повторной подачи старого вывода в контекст.

### 3.2. Простота установки

После установки пакета и регистрации одного local MCP-сервера не требуется:

- создавать конфигурационный файл;
- заводить inventory;
- настраивать `pass`;
- переносить SSH config в другой формат;
- выпускать отдельные правила для каждого устройства.

Для SSH нужен системный `ssh`, для Telnet — системный `telnet`. Serial работает
через Python-зависимость `pyserial`.

## 4. Не входит в 0.2.0

- Одноразовые `run_command` / `run_commands`.
- Vendor-specific драйверы и автоматический выбор CLI-команд.
- Prompt-driven command gateway.
- Inventory и именованные connection profiles.
- Sandbox, command allowlist и фильтрация SSH-опций.
- Обязательное подтверждение `open_session` средствами MCP.
- Перенос старого structured API под видом compatibility mode.
- Windows PTY backend. Первый целевой runtime — POSIX, в первую очередь Linux.
- Сетевой/remote MCP listener: сервер остаётся локальным stdio-процессом.

## 5. Целевой MCP-контракт

Остаются семь инструментов:

```text
open_session
terminal_write
terminal_read
terminal_write_secret
read_output
session_status
close_session
```

### 5.1. `open_session`

Единственный обязательный аргумент:

```json
{
  "command": "ssh -J operator@bastion.example.net operator@192.0.2.10"
}
```

Другие примеры:

```json
{"command": "ssh -i ~/.ssh/id_ed25519 -p 2222 operator@192.0.2.20"}
```

```json
{"command": "telnet 192.0.2.30 23"}
```

```json
{"command": "serial /dev/ttyUSB0 115200"}
```

Аргументы `host`, `protocol`, `port`, `credentials`, `route`,
`host_key_policy`, `legacy`, `allow_telnet`, `allow_serial`,
`allow_plaintext_password` и `serial` удаляются.

Неизвестные поля отклоняются с сообщением, что подключение задаётся через
`command`.

### 5.2. Остальные инструменты

Сигнатуры основного I/O сохраняются:

```text
terminal_write(session_id, data, enter=true)
terminal_read(session_id, timeout=null)
read_output(session_id, offset=null, limit=null)
session_status(session_id)
close_session(session_id)
```

`terminal_write_secret` получает новый контракт, описанный в разделе 9.

## 6. Команды подключения

### 6.1. Общий разбор

- Строка разбирается через `shlex.split(..., posix=True)`.
- Shell для запуска не используется.
- Пустая команда и команда без аргументов отклоняются.
- Поддерживаемые первые слова: `ssh`, `telnet`, `serial`.
- Для `ssh` и `telnet` аргументы передаются клиенту без фильтрации опций.
- Сервер не пытается определить, интерактивная ли это команда: время жизни
  сессии определяется временем жизни процесса.

Отсутствие shell означает, что локальные `&&`, `|`, подстановки и redirection не
выполняются самим MCP. Аргументы SSH, включая те, которые OpenSSH сам использует
для запуска команд, не фильтруются.

### 6.2. SSH

SSH реализуется как запуск системного OpenSSH в отдельном PTY:

```text
open_session(command)
  -> shlex.split
  -> resolve ssh executable
  -> spawn OpenSSH in PTY
  -> persistent raw terminal
```

Сервер наследует окружение MCP-процесса. Поэтому работают:

- `~/.ssh/config` и aliases;
- SSH agent и добавленные в него ключи;
- `ProxyJump`, `ProxyCommand` и jump-конфигурация;
- `IdentityFile`, `IdentitiesOnly`, `StrictHostKeyChecking`;
- `KexAlgorithms`, `HostKeyAlgorithms`, `Ciphers` и другие legacy-настройки;
- обычные сообщения OpenSSH об ошибках.

Сервер больше не имеет собственного known_hosts store и не дублирует host key
policy. Проверка ключей выполняется OpenSSH по правилам пользователя и переданной
команды.

### 6.3. Telnet и TCP console

Telnet запускается системным `telnet` в PTY. TCP console — это тот же режим с
другим портом:

```text
telnet 192.0.2.30 23
telnet 192.0.2.31 2001
```

Если executable отсутствует, возвращается `executable_not_found` с указанием
имени отсутствующего клиента. Отдельного `console` protocol больше нет.

### 6.4. Serial

Serial — встроенная короткая команда:

```text
serial DEVICE [BAUDRATE]
```

Правила:

- `DEVICE` обязателен и должен быть существующим character device;
- `BAUDRATE` по умолчанию `9600`;
- остальные параметры первой версии: `8N1`;
- чтение/запись реализуются через `pyserial`, без внешнего terminal client;
- ошибки отсутствующего устройства, permissions и занятого порта возвращаются с
  конкретным текстом.

Пример:

```text
serial /dev/ttyUSB0 115200
```

## 7. Жизненный цикл и терминальный I/O

### 7.1. Запуск

Для SSH/Telnet создаётся процесс в PTY, для Serial — `SerialTerminal`.

`open_session` использует короткое стартовое окно чтения:

- если процесс успел завершиться, вызов возвращает ошибку с exit code и
  накопленным stderr/stdout;
- если процесс жив и вывод стабилизировался, возвращается активная сессия;
- если процесс жив, но начального вывода нет, сессия также возвращается с
  warning, а не считается failed.

`ready` означает «терминал создан и к нему можно писать», а не «аутентификация
завершена» и не «CLI prompt найден». Password prompt, host key prompt и banner —
обычный вывод новой сессии.

Автоматическое best-effort определение prompt удаляется. Модель смотрит живой
поток через `terminal_read`.

### 7.2. Чтение

Сохраняется текущий проверенный контракт:

- `terminal_read` возвращает только новый вывод;
- чтение завершается после короткой тишины или по `timeout`;
- не требуется prompt или известный dialect;
- pager, password prompt, echo, banner и ошибки возвращаются как есть;
- при `truncated=true` используется `next_output_offset`;
- `read_output()` без offset продолжает с read cursor;
- явный offset нужен только для осознанного чтения старого буфера;
- повторный вызов без новых данных не реинжектирует историю в контекст.

### 7.3. Запись

- `terminal_write` отправляет точную UTF-8 строку;
- `enter=true` добавляет `\n` для PTY и `\r` для Serial;
- `enter=false` используется для одиночных клавиш и control bytes;
- содержимое не разбирается и не заменяется сервером;
- запись в завершившийся процесс возвращает конкретную ошибку состояния.

### 7.4. Завершение

Состояния:

```text
ready -> closing -> closed
   |          ^
   v          |
 failed ------
```

- `close_session` завершает процесс/serial и освобождает ресурсы;
- естественный выход процесса сохраняет оставшийся вывод, exit code и состояние;
- закрытая сессия остаётся доступной для `session_status` до её удаления;
- при завершении MCP-процесса все дочерние PTY-процессы и serial connections
  закрываются, чтобы не оставлять осиротевшие клиенты;
- автоматический idle timeout и hard lifetime по умолчанию убираются: соединение
  живёт до `close_session`, выхода удалённой стороны или остановки MCP;
- встроенный лимит одновременных сессий — 10; превышение возвращает обычную
  `session_error`.

## 8. Модель ошибок

### 8.1. Главное исправление

На MCP-границе все ожидаемые `NetworkMCPError` преобразуются в
`mcp.server.mcpserver.exceptions.ToolError`.

```python
try:
    result = await manager_operation(...)
except NetworkMCPError as exc:
    raise ToolError(str(exc)) from exc
```

Неожиданные внутренние исключения продолжают обрабатываться SDK как crash без
раскрытия traceback модели.

### 8.2. Требования к сообщениям

Сообщение должно содержать:

- стабильный код;
- что именно произошло;
- полезный исходный stderr/текст системной ошибки;
- только безопасную для журнала информацию.

Примеры:

```text
executable_not_found: telnet executable was not found on PATH
```

```text
transport_error: ssh exited with code 255 during startup:
Host key verification failed.
```

```text
session_error: unknown or expired session <id>
```

```text
credential_error: secret file is not readable: <path>: <os error>
```

Не допускается заменять эти сообщения общим `Error executing tool ...`.

### 8.3. Ошибки после открытия

Не каждая ошибка подключения обязана стать исключением `open_session`: часть
проявляется после возврата живой сессии. Поэтому:

- исходный вывод OpenSSH/Telnet остаётся доступен через `terminal_read`;
- `session_status` сообщает `failed`/`closed`, exit code и сохранённую ошибку;
- запись в failed/closed session возвращает внятное исключение;
- ранняя ошибка, успевшая завершить процесс в стартовом окне, возвращается из
  `open_session` сразу.

Размер ошибочного вывода ограничивается последними несколькими KiB, чтобы сбой не
возвращал в контекст весь session transcript.

## 9. Секреты

### 9.1. Новый `terminal_write_secret`

Передаётся ровно один источник:

```json
{"session_id": "...", "value": "secret"}
```

```json
{"session_id": "...", "env": "DEVICE_PASSWORD"}
```

```json
{"session_id": "...", "file": "/path/to/secret"}
```

Семантика:

- `value` — использовать строку напрямую;
- `env` — прочитать переменную окружения MCP-процесса;
- `file` — прочитать файл и удалить один завершающий CR/LF;
- пустое значение и несколько источников одновременно — ошибка;
- перевод строки для живого prompt добавляется по правилам транспорта;
- значение добавляется в redaction текущей сессии;
- результат содержит только `session_id`, тип источника, число байт и состояние;
- в audit попадают только тип источника и число байт, не само значение.

Старый `entry` и обязательная интеграция с `pass` удаляются.

### 9.2. Plaintext

`value` поддерживается как удобный режим без настройки. При этом документация
явно указывает: значение уже находится в аргументах вызова, контексте модели и
истории клиента. Отсутствие пароля в ответе модели не исключает это хранение.

Поэтому рекомендуемый порядок — `env` или `file`, а `value` — простой fallback.
Дополнительного plaintext opt-in флага нет.

Если секрет передать обычным `terminal_write` или прямо в `command`, сервер не
может гарантировать его удаление из истории клиента и audit. После регистрации
секрета через `terminal_write_secret` его последующие вхождения в выводе
маскируются redactor.

## 10. Конфигурация и зависимости

### 10.1. Конфигурация

Обязательная конфигурация отсутствует. Runtime defaults встроены в код:

- output buffer;
- read quiet period и max read timeout;
- startup read window;
- max open sessions;
- audit path в XDG state directory.

Удаляются:

- `policy.yml` и connection policy;
- connection/credential resolver;
- собственный known_hosts;
- настройки host key policies;
- per-call allow flags;
- idle/lifetime policy;
- обязательная интеграция с `pass`.

Команда `network-terminal-mcp check` проверяет фактическую готовность:

- версию пакета;
- доступность `ssh` и `telnet`;
- доступность audit directory;
- serial dependency;
- отсутствие необходимости в конфигурационных файлах.

### 10.2. Зависимости

Целевой набор:

- MCP SDK и Pydantic;
- `ptyprocess` для POSIX PTY;
- `pyserial` для Serial;
- YAML/config/Paramiko/telnetlib3/SOCKS-specific зависимости удаляются, если
  после рефакторинга не используются elsewhere.

Платформа первой версии — POSIX/Linux. Classifiers и документация обновляются,
чтобы не обещать неподдерживаемый Windows PTY.

## 11. Модель доверия и аудит

### 11.1. Модель доверия

Сервер является доверенным локальным компонентом с правами пользователя, а не
sandbox.

Настоящий OpenSSH с неограниченными аргументами может запускать локальные команды
через собственные опции. Поэтому сервер не заявляет, что разрешает «только
сетевые подключения». Это осознанная модель «сначала функциональность».

Обязательного permission popup для `open_session` нет. Клиент может добавить
собственные permissions позже, но они не являются частью обязательной установки.

### 11.2. Аудит

JSONL-аудит сохраняется:

- `open_session`: полная команда, outcome, ошибка, session ID;
- `terminal_write`: ввод после redaction, enter, bytes, outcome;
- `terminal_write_secret`: источник и bytes, без значения;
- `terminal_read`/`read_output`: offsets, bytes и cursor;
- `session_status` и `close_session`: состояние и exit information;
- correlation ID и timestamps.

Pre-action audit остаётся fail-closed: если запись о старте действия невозможна,
действие не выполняется. Каталоги `0700`, файлы `0600`.

Аудит — не permission gate: он не требует интерактивного подтверждения и не
фильтрует команду.

## 12. Целевая архитектура

```text
OpenCode / MCP client
  |
  | stdio
  v
server.py
  |-- ToolError boundary for expected errors
  |-- usage instructions + usage resource
  v
SessionManager
  |-- command parsing / serial validation
  |-- session lifecycle and per-session lock
  |-- bounded output + read cursor
  |-- secret resolution and redaction
  |-- audit
  |
  +-- PtyTerminal (ssh / telnet via ptyprocess)
  |
  +-- SerialTerminal (pyserial)
```

Никаких vendor adapters, connection plans, host-key stores, SOCKS routers,
Paramiko jump clients и policy gates.

## 13. Изменения по файлам

### 13.1. `server.py`

- Оставить только `open_session(command: str)`.
- Добавить единый `NetworkMCPError -> ToolError` boundary.
- Обновить descriptions всех инструментов.
- Обновить `terminal_write_secret` под `value`/`env`/`file`.
- Сохранить usage resource и короткие instructions.

### 13.2. `sessions/manager.py`

- Удалить OpenSpec/ConnectionPlan/credential/host-key/route сборку.
- Открывать `PtyTerminal` или `SerialTerminal` по разобранной команде.
- Сохранить locking, buffer, cursor, redaction, audit и cleanup.
- Убрать prompt probing, idle/lifetime expiry и route metadata.
- Добавить отслеживание process exit и exit code.

### 13.3. `sessions/models.py`

`SessionInfo` содержит:

- `session_id`;
- `command`;
- `state`;
- `created_at` и `last_used_at`;
- `warnings`;
- опциональные `exit_code` и `error`.

Поля `host`, `route` и `prompt` удаляются. I/O result models сохраняются с
минимальными изменениями; `TerminalSecretResult` больше не возвращает `entry`.

### 13.4. `terminal.py`

- Добавить generic `PtyTerminal` на `ptyprocess`.
- Оставить единый transport protocol для read/write/close/is_alive.
- Serial выделить в отдельный модуль или оставить рядом без Paramiko-кода.
- Удалить `SshTerminal`, `TelnetTerminal`, Paramiko и telnetlib3.

### 13.5. Удаляемые компоненты

После переноса поведения и тестов удаляются:

- `config/`;
- `connections/`;
- `credentials/pass_backend.py`;
- `host_keys.py`;
- `socks.py`;
- старые connection/policy/credential tests;
- связанные зависимости и документация.

`redaction.py`, `audit.py`, `errors.py` сохраняются и упрощаются только при
необходимости.

### 13.6. `__main__.py` и `pyproject.toml`

- `check` переводится на проверку runtime prerequisites.
- Обновляются dependencies, version `0.2.0`, classifiers и package metadata.
- Console script и stdio entry point сохраняются.

## 15. Тестовая стратегия

### 15.1. Unit

- разбор SSH/Telnet/Serial команд;
- пустая и неподдерживаемая команда;
- отсутствие executable;
- serial defaults и ошибки устройства;
- ровно один secret source;
- env/file/value resolution и пустой секрет;
- `NetworkMCPError -> ToolError` с сохранением сообщения;
- unexpected exception остаётся crash без утечки internals;
- redaction секрета во вводе, выводе и ошибках;
- process exit code и failed/closed transitions;
- cleanup дочерних процессов.

### 15.2. PTY integration без реальных устройств

Использовать поддельные `ssh`/`telnet` executables во временной директории и PATH:

- запуск и начальный banner;
- persistent write/read в одном процессе;
- несколько команд подряд без переподключения;
- password prompt и ввод через secret tool;
- ранний exit с stderr и ненулевым кодом;
- выход после успешного открытия;
- pager/control keys;
- большой вывод, truncation и cursor offsets;
- отсутствие повторной выдачи уже прочитанного;
- закрытие process group при `close_session` и shutdown.

Реальные сетевые устройства для автоматических тестов не нужны.

### 15.3. Сохраняемые регрессии

Все существующие тесты output cursor, bounded buffer, audit и redaction должны
быть перенесены на новый transport interface без ослабления проверок.

### 15.4. Проверки проекта

```bash
uv run ruff check .
uv run mypy src
uv run pytest
```

Дополнительно:

- stdio initialize + tools/list;
- вызов `session_status` с несуществующим ID возвращает текст ошибки;
- установленный wheel проходит тот же smoke test;
- `network-terminal-mcp check` работает из чистой установки.

### 15.5. Живая проверка

Только с отдельного разрешения пользователя для конкретных целей и команд:

- SSH с agent/config;
- SSH с интерактивным password/passphrase;
- Telnet/TCP console;
- Serial при наличии hardware;
- unknown host key, неверные credentials и недоступный target.

## 17. Критерии приёмки

1. Чистая установка не требует ни одного конфигурационного файла.
2. `open_session` имеет только `command`, без старых structured-полей.
3. SSH использует существующие config/agent без повторного описания ключей и
   маршрутов.
4. Password prompt обрабатывается через `terminal_write_secret` без смены
   сессии.
5. Telnet и Serial открываются короткими командами.
6. Несколько команд выполняются в одном живом терминале.
7. Повторное чтение не дублирует старый вывод.
8. Ошибка подключения содержит настоящий stderr/причину, а не общую заглушку.
9. Неизвестная сессия и ошибки I/O также возвращают конкретные сообщения.
10. Значение секрета не попадает в audit и результат secret tool.
11. MCP не требует обязательного permission popup.
12. Все инструменты видны модели напрямую при рекомендуемой конфигурации
    OpenCode.
13. Дочерние процессы не остаются после `close_session` и остановки сервера.
14. `ruff`, `mypy`, `pytest` и wheel smoke проходят.
15. Документация и фактическое поведение не противоречат друг другу.

## 18. После 0.2.0

Ограничители рассматриваются только по фактическим проблемам эксплуатации.
Возможные, но не запланированные направления:

- опциональные client-side permissions;
- опциональные transcript files;
- дополнительные terminal clients через тот же command dispatcher;
- resource limits, если появятся реальные утечки или злоупотребления;
- Windows PTY, если появится потребность.

Эти возможности не должны задерживать или усложнять базовый релиз.
