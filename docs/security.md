# Модель безопасности

## Границы доверия

MCP запускается локально через `stdio` и даёт модели сырой терминал к сетевым
устройствам, включая возможность печатать `ssh`, `telnet` и команды
конфигурации. Он считается привилегированным компонентом доверенного оператора.
Ответ модели, пользовательский текст и вывод устройства не считаются
доверенными командами.

MCP не заменяет TACACS/RADIUS command authorization и не пытается обходить её.
Для production предпочтительна отдельная read-only AAA-учетная запись.

## Секреты

- Соединение описывается моделью в `open_session`; секреты в описании — только
  ссылки: имя записи `pass` или явный локальный key file.
- `pass` вызывается сервером без shell interpolation; имя записи валидируется
  (относительное, без `..`, `/` в начале и пробелов).
- `terminal_write_secret(session_id, entry)` — единственный правильный способ
  ввести пароль, passphrase или другой секрет в живой prompt. Значение
  разрешается внутри сервера, пишется в поток, добавляется в redaction сессии и
  никогда не возвращается в аргументах, результатах и audit; журналируются
  только имя entry и число байт.
- Обычный `terminal_write` логирует ввод целиком (с masking известных
  серверу секретов). Если модель напечатает секрет обычным `terminal_write`, он
  окажется в audit — это ошибка вызывающей стороны, а не скрытая утечка.
- Пароли не передаются в MCP arguments, tool results, transcripts и audit.
- Redaction применяется к исключениям до логирования.
- Сервер не предоставляет инструмент для чтения произвольной записи `pass`,
  кроме ввода её значения в терминал через `terminal_write_secret`.

Plaintext-пароль при открытии сессии — исключение с двойным гейтом: он
принимается только при `allow_plaintext_password=true` в самом вызове, не
сохраняется сервером, маскируется в аудите и всегда возвращает insecure warning.
Пароль при этом остаётся в контексте модели и может быть виден в
permission-попапе и логах клиента — это осознанный компромисс, а не режим по
умолчанию.

Рекомендуемый формат записи `pass`:

```text
<password on first line>
```

AAA username не является секретом и задаётся рядом со ссылкой; отдельный enable
secret хранится отдельной записью `pass`.

## Права ввода

`terminal_write` не фильтрует содержимое по синтаксису: это сырой терминал.
Границей является клиентское подтверждение подключения и профиль доверия
оператора:

- `open_session` проходит через нативный permission-попап OpenCode
  (`network-terminal_open_session: ask`): пользователь видит host, route,
  protocol и credential-ссылки до подключения.
- `terminal_write` / `terminal_read` / `terminal_write_secret` по умолчанию
  popup не вызывают: после одобренного подключения модель работает в устройстве
  без per-команды подтверждений. Оператор может добавить
  `"network-terminal_terminal_write": "ask"` в permission-политику клиента,
  если предпочитает подтверждать каждый ввод; сервер это не контролирует.
- `terminal_write_secret` использует только backend `pass`: значение
  подставляется сервером и не раскрывается модели.
- Позже поверх raw terminal можно добавить распознавание sensitive-команд
  (`conf t`, `system-view`, `commit`, `reload`) с вынесенным в клиент
  подтверждением. В текущей версии такого фильтра нет.

## Аудит

Каждая операция получает correlation ID. JSONL-запись содержит:

- время и session ID;
- host, protocol и route (direct/socks/proxyjump/telnet/console/serial);
- пользователя AAA, но не пароль;
- event/tool: `open_session`, `terminal_write` (полный ввод, redacted),
  `terminal_write_secret` (entry и размер, без значения), `terminal_read`
  (размер), `close_session`;
- решение policy-гейтов подключения, outcome и размер вывода;
- ошибки после redaction.

Если pre-action audit-файл недоступен, операция не выполняется. Права файлов:
каталоги 0700, файлы 0600. Full transcripts не реализованы;
`transcripts_enabled` пока является зарезервированной настройкой.

## Model-described connections

Модель выбирает и host, и route, и credential-ссылку. Основной компенсационный
контроль — нативный permission-попап OpenCode. Сервер не проверяет клиентское
подтверждение криптографически. Использование сервера напрямую по stdio, вне
permission-политики клиента, лишено этого гейта и допустимо только в доверенном
окружении.

Дополнительно Pydantic (`extra="forbid"`) не принимает неизвестные поля, поэтому
случайные `password`/`secret`/`platform` в описании соединения отклоняются;
сервер валидирует спецификацию до открытия сокета и пишет в audit только host,
protocol, route и несекретные детали.

## Legacy SSH

Слабые алгоритмы включаются только per-call для явного host через
`legacy: {host_key_algorithms, kex_algorithms, ciphers}`. Запрещено изменять
глобальный `~/.ssh/config` шаблоном `Host *`; глобальные настройки Paramiko не
ослабляются.

Каждое legacy-соединение возвращает предупреждение и отмечается в audit. Явные
списки ограничивают только перечисленные категории (allowlist → Paramiko
`disabled_algorithms`); остальные категории сохраняют значения Paramiko по
умолчанию. Host key checking остается включенным: default
`host_key_policy: strict` сверяет ключ с локальным `known_hosts`. Для первичной
регистрации допускается только явный `accept_new` (TOFU), который сохраняет
fingerprint в аудит; затем нужно вернуться в `strict`.

`accept_changed` — слабый доверительный режим для устройств, у которых host key
заведомо меняется при каждой загрузке (например, некоторые SNR). Он допустим
только как явный opt-in и при каждой смене ключа пишет в audit предупреждение со
старым и новым fingerprint. Этот режим не защищает от MITM.

## ProxyJump и SOCKS5

Один SSH jump host задаётся полем `route` в `open_session`. Сервер сначала
проверяет и аутентифицирует bastion, затем открывает Paramiko `direct-tcpip`
channel и проверяет key final target через этот channel. Password и host key
policy у hop и final target независимы; оба password добавляются в redaction.

Literal `ProxyCommand`, shell command, automatic agent/key discovery и system
host keys не используются. Поддерживаются только один hop и SSH forwarding;
запрет forwarding на bastion, ошибка проверки key или target login закрывают
весь маршрут fail-closed.

Локальный SOCKS5-маршрут `route: {type: "socks", host, port}` строит минимальный
SOCKS5 CONNECT (no-auth), не принимает proxy credentials и не резолвит имена:
target обязан быть IP-адресом. Доверие к локальному прокси — на операторе;
сессия всегда возвращает warning.

## Telnet, console и serial

Telnet и TCP console разрешаются только явно: `allow_telnet=true` в самом
вызове; policy `defaults.allow_telnet: false` запрещает режим полностью.
Учётные данные и трафик передаются открытым текстом, host key не проверяется,
предупреждение обязательно. Автоматический fallback с SSH на Telnet запрещен.

Локальная serial-консоль требует `allow_serial=true` и абсолютного пути
`/dev/tty*`, который должен существовать и быть символьным устройством.
Аутентификации и транспорта защиты нет; policy `defaults.allow_serial: false`
может запретить режим полностью. Serial-сессия всегда возвращает warning.

## Изменения конфигурации

Изменения не отделены отдельным инструментом: сырой терминал позволяет модели
вводить `configure terminal`, `system-view`, `commit` и подобные команды так же,
как это делает инженер в обычном `ssh`. Ответственность за изменение лежит на
операторе и AAA-политике устройства; MCP не даёт модели скрытого способа
замаскировать изменение под диагностику, потому что весь ввод виден в audit.

Клиентская граница остаётся рекомендуемой точкой контроля: оператор может
настроить `permission` для `terminal_write` в OpenCode (см. «Права ввода»).
Сессии живут в памяти процесса и не переживают рестарт: после рестарта сессии
нет, операции с её ID fail-closed. Ранее отправленные команды могли примениться;
автоматического повтора нет.
