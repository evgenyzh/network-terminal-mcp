# Результаты проверок 0.5.0

## Проверка 0.5.0

9 ноября 2026 года: 127 тестов, Ruff и mypy прошли; wheel установлен в
отдельное окружение и проверен командой `network-terminal-mcp check`.

С разрешения пользователя предрелизный MCP проверен по SSH на том же сетевом
устройстве без установки `NETWORK_TERMINAL_DSR` и без явного `\r`: вход по
паролю и `terminal_write("show version")` вернули результат. Другие реальные
устройства и протоколы в этом сценарии не проверялись.

## Проверка 0.4.0

9 ноября 2026 года: `uv run pytest` — 127 passed; `uv run ruff check .`,
`uv run mypy src`, `git diff --check` — успешно. Wheel установлен в отдельное
окружение, команда `network-terminal-mcp check` прошла.

С отдельного разрешения на конкретное устройство предрелизный код проверен по
SSH: вход по паролю, опциональные DSR-ответы и read-only команда завершились
успешно через MCP stdio. Для этого CLI потребовался `\r` вместо стандартного
для SSH `\n`. Реальные идентификаторы, содержимое ответа и секреты не включены.
Граница 65 536 байт проверяется автоматическими тестами; реальный Serial и
Telnet в этом выпуске не проверялись. Автотесты не подтверждают полноценную
терминальную эмуляцию или бинарный протокол на оборудовании.

## Что именно подтверждено

- `open_session(command)` принимает только `command`; старые structured-поля
  отклоняются.
- SSH/Telnet запускаются как реальные процессы в PTY и сохраняют состояние
  между вызовами.
- Первый `terminal_read` возвращает стартовый banner, не теряя его.
- Ранний exit возвращает exit code и реальный stderr.
- Password prompt обрабатывается `terminal_write_secret`; значение отсутствует
  в результате и audit.
- Cursor-чтение не повторяет уже прочитанный вывод.
- `truncated=true` и `next_output_offset` позволяют продолжить чтение.
- Неожиданная внутренняя ошибка не раскрывает модели traceback.
- stdio-вызов с неизвестной сессией возвращает:
  `session_error: unknown session ...`, а не общую заглушку.
- `close_session` и shutdown закрывают дочерние PTY.
- PTY-запись с нечитающим клиентом завершается по `write_timeout`, а не висит.
- После write timeout сессия переходит в `failed`, но `close_session` работает.
- `last_output_at` не обновляется пустым чтением; `idle_seconds` растёт, пока
  нового вывода нет.

## Живая SSH-проверка

С разрешения пользователя предрелизный код 0.3.0 подключён по SSH к Linux-хосту
с существующей локальной настройкой и ключом. Проверены banner, запись простой
команды, чтение ответа, пустое повторное чтение и закрытие. При закрытии процесс
SSH вернул код 255; состояние сессии — `closed`. Граница 65 536 байт проверена
автоматически, а не на живом хосте.

Ранее для 0.2.0 выполнена проверка через jump host:

С отдельного разрешения выполнена одна проверка через реальный OpenSSH и jump
host:

- host key prompt обработан; fingerprint сверен с уже известным ключом, в
  документацию не записан;
- вход по SSH-ключу без интерактивного пароля;
- открыт persistent shell на тестовом Linux-хосте;
- в одной сессии выполнены `hostname`, `whoami`, `pwd`, `uname -sr`;
- повторное чтение не вернуло старую историю;
- сессия закрыта через `close_session`.

Ручное закрытие OpenSSH завершилось с кодом 255 из-за SIGHUP; это ожидаемое
следствие принудительного закрытия PTY, состояние сессии — `closed`.

## Что не проверялось

- Реальные сетевые устройства и интерактивный ввод пароля.
- Реальный Telnet/TCP console terminal server.
- Реальный serial-кабель `/dev/ttyUSB*`.
- Windows PTY.
- Длительная эксплуатация и ротация audit.

Остальные живые проверки требуют отдельного разрешения на конкретные цели и
команды. Реальные адреса, hostnames, usernames и fingerprints в документ не
включаются.
